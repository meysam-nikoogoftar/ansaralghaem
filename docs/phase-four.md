# فاز چهار — انتقال ورود و ثبت‌نام

تاریخ بررسی: ۲۱ نوامبر ۲۰۲۶. کد روی `change-framework` آماده است؛ هنوز کامیت یا منتشر نشده است.

## خروجی

| مسیر | صفحهٔ سرور | کامپوننت فرم |
|---|---|---|
| `/login` | `frontend-next/app/(auth)/login/page.tsx` | `components/auth/login-form.tsx` |
| `/register` | `frontend-next/app/(auth)/register/page.tsx` | `components/auth/register-form.tsx` |

برند، ورودی‌ها و ساختار HTML اولیه روی سرور آماده می‌شوند. `AuthCard`، `AuthField`، `AuthFeedback` و hook تایپ‌شدهٔ `useAuthSubmission` مشترک‌اند. schemaهای ورودی مستقل از UI و تایپ‌های دامنه در `types/index.ts` هستند؛ کتابخانهٔ فرم جدیدی اضافه نشده است.

## نشست و مرز دو اپ

- قرارداد JWT و کلیدهای `access_token` و `refresh_token` حفظ شده‌اند؛ Next و داشبورد/مدیریت Vite از همان origin استفاده می‌کنند.
- `returnTo` در سرور و پیش از هدایت کلاینت اعتبارسنجی می‌شود. query و hash معتبر هنگام تغییر login/register و پس از ورود حفظ می‌شوند؛ مقصد خارجی یا حلقهٔ ورود به `/dashboard` برمی‌گردد.
- موفقیت به مقصد متعلق به Next با router.replace و به مقصد Vite با navigation کامل می‌رود. بررسی نشست Vite پس از ورود با header Bearer انجام می‌شود.
- redirectهای برنامه‌ای React Router از مسیر خصوصی نیز با bridge به Next می‌رسند و state مقصد به query تبدیل می‌شود. صفحهٔ قدیمی ورود دیگر در bundle اصلی Vite import نمی‌شود؛ فایل آن برای rollback باقی است.
- رویداد storage خروج را میان تب‌های دو اپ همگام می‌کند. پاسخ دیرهنگام پروفایل Vite بعد از خروج نادیده گرفته می‌شود؛ درخواست قدیمی refresh نیز نمی‌تواند توکن حساب جدید را پاک کند یا با هویت جدید retry شود.
- اگر ذخیرهٔ یکی از توکن‌ها شکست بخورد، توکن ناقص پاک می‌شود و خطای قابل پیگیری در همان فرم می‌ماند.

## اعتبارسنجی و امنیت

- شمارهٔ موبایل فارسی/عربی به رقم ASCII تبدیل می‌شود و قالب `09` همراه ۱۱ رقم بررسی می‌شود. نام‌ها trim و محدود به ۱۰۰ نویسه‌اند.
- رمز عبور بدون تغییر به سرور می‌رود؛ برای ثبت‌نام حداقل ۶ نویسه و تطابق تکرار رمز مطابق قرارداد فعلی بررسی می‌شود. رمز در URL، storage، گزارش یا metadata قرار نمی‌گیرد و تکرار رمز در JSON ارسال نمی‌شود.
- schema فیلدهای اضافه از جمله نقش/مجوز تزریقی را به payload فرم راه نمی‌دهد. سرور همچنان مرجع کنترل مجوز و ثبت حساب است.
- قفل synchronous ارسال از کلیک/submit تکراری پیش از rerender جلوگیری می‌کند. درخواست هنگام خروج از فرم abort می‌شود؛ نتیجهٔ درخواست superseded نمی‌تواند نشست را دوباره فعال کند.
- خطاهای فیلدی، ورود ناموفق، محدودیت 429 و خطای شبکه/سرویس، جدا از loading نمایش داده می‌شوند. مقدار فیلدها برای اصلاح و retry حفظ می‌شود و خطا با label و aria-describedby به ورودی مرتبط است.
- فرم HTML دارای `method="post"` است و پیش از اجرای کلاینت/بررسی اولیهٔ نشست، submit غیرفعال است؛ نبود JavaScript باعث ارسال رمز در query نمی‌شود.
- CSP با nonce، headerهای امنیتی و private/no-store روی هر دو مسیر اعمال می‌شوند. درخواست JSON این کلاینت فقط Bearer موردنیاز را می‌فرستد و cookie ارسال نمی‌کند.
- مهاجرت به cookie HttpOnly/BFF و SSR خصوصی انجام نشده؛ localStorage برای هم‌زیستی فعلی لازم است. محدودیت نرخ سمت سرور و HTTPS باید در بک‌اند/استقرار اعمال شوند؛ قفل ارسال مرورگر rate limit سرور نیست.

## سرعت و SEO

- فرم‌ها به دریافت اولیهٔ داده از Django وابسته نیستند. برای مهمان بدون توکن، درخواست پروفایل اضافه اجرا نمی‌شود؛ اگر توکن قبلی وجود دارد پیش از هدایت مجدد بررسی می‌شود.
- فونت محلی، لوگوی کوچک با ابعاد ثابت/preload و CSS مخصوص auth استفاده می‌شود. WebGL و کد سه‌بعدی اپ قدیمی در این دو صفحه بارگیری نمی‌شوند.
- هر صفحه عنوان و canonical مستقل و `noindex,nofollow` دارد؛ auth در sitemap وارد نمی‌شود. نمایش اولیهٔ فرم از سرور است، اما ورود با قرارداد JWT/localStorage نیازمند JavaScript است.
- اندازهٔ script دریافتی در تست production محلی حدود ۱۸۴ کیلوبایت encoded بود. DOMContentLoaded در اجراهای محلی سریع بود؛ جزئیات در JSON مرجع ثبت شده و معادل Lighthouse یا تضمین سرعت شبکهٔ کاربر نیست.
- حذف import صفحات auth قدیمی، bundle اصلی Vite را نیز کوچک‌تر کرد. هشدار قدیمی chunkهای بزرگِ بخش‌های مهاجرت‌نکرده باقی است.

## بررسی‌های انجام‌شده

- TypeScript strict، build Next، lint/build Vite و تست‌های واحد هر دو اپ موفق‌اند؛ مجموعهٔ Next اکنون ۹ تست واحد دارد.
- مجموعهٔ مرورگر production با API fixture مستقل اجرا شد و هیچ حساب واقعی ایجاد نشد.
- ظاهر login و register در دسکتاپ 1440 روشن و موبایل 390 تیره بازبینی شد؛ overflow افقی و خطای JavaScript/تصویر مشاهده نشد.
- HTML اولیه، POST بودن فرم، noindex، canonical، CSP و submit غیرفعال بدون JavaScript بررسی شدند.
- ورود از مسیر خصوصی Vite، حفظ مقصد در تغییر فرم‌ها، ورود ناموفق، 429، رقم فارسی، ارسال موفقِ یکتا و بازیابی نشست در داشبورد Vite پاس شدند.
- عدم تطابق رمز، خطاهای چندفیلدی بک‌اند، حفظ دادهٔ فرم، 503 و retry ثبت‌نام، حذف password2/نقش از JSON و مقصد پیش‌فرض امن پاس شدند.
- خروج هم‌زمان تب Next و دو تب Vite و خرابی جزئی ذخیره‌سازی مرورگر پاس شدند.
- تست‌های قبلی صفحات عمومی، پیش‌نویس مقاله، کامنت/پاسخ، 404 و گالری نیز پاس مانده‌اند.
- پیش‌نمایش production روی پورت 3000 با Django واقعی نیز به شکل فقط‌خواندنی بررسی شد: هر دو فرم آماده، عنوان/noindex/CSP درست و مقصد مسیر خصوصی محفوظ بود؛ هیچ درخواست ورود یا ثبت‌نام به حساب واقعی ارسال نشد.

شواهد و تصاویر منتخب در [phase-four-baseline](phase-four-baseline/) و خروجی کامل در `frontend-next/.test-artifacts/phase-two` نگه داشته می‌شوند. نام پوشهٔ تست قبلی حفظ شده چون اکنون مجموعهٔ یکپارچهٔ فازهای دو و چهار است. CI همین مجموعه را اجرا می‌کند؛ اجرای remote CI در این جلسه انجام نشده است.

## اجرا و rollback

دستورهای توسعه و تست در [README پوسته](../frontend-next/README.md) قرار دارند. برای پیش‌نمایش production محلی، Django روی 8000، Nginx خروجی Vite روی 5174 و Next روی 3000 اجرا می‌شوند. فقط برای آزمون خودکار، fixture روی 8101 و Next آزمایشی روی 3100 اجرا می‌شود.

برای rollback، routeهای auth جدید، مالکیت `/login` و `/register`، matcher مربوط به auth در `proxy.ts` و جایگزینی routeهای legacy در یک تغییر هماهنگ برگردند. حفظ فقط یکی از این بخش‌ها می‌تواند حلقهٔ redirect یا مشکل CSP در توسعهٔ Vite ایجاد کند. فایل‌های قدیمی auth حذف نشده‌اند.
