# برنامهٔ مرحله‌به‌مرحلهٔ انتقال کامل اپ به Next.js

این برنامه بر اساس مسیرهای فعلی `frontend/src/App.jsx` نوشته شده است. هدف، انتقال تدریجی ۳۲ صفحهٔ مسیردار و صفحهٔ 404 از React/Vite به Next App Router با حفظ URL، رفتار، ظاهر، نقش‌های کاربری و قراردادهای Django است. چک‌باکس‌ها وضعیت پیشنهادی کار هستند؛ وجود این سند به معنی انجام مهاجرت نیست.

## معماری و قواعد ثابت

- `frontend-next` ورودی مشترک روی پورت 3000 است؛ `frontend` تا پایان مهاجرت مستقل باقی می‌ماند.
- مسیرهای تعریف‌شده در Next از همان اپ پاسخ می‌گیرند و باقی مسیرها با fallback به Vite می‌روند. راهنمای اجرای پایه در [next-migration.md](next-migration.md) است.
- هر صفحه یک واحد تحویل و بازگشت است. ابتدا در محیط آزمایشی منتقل شود، سپس پس از عبور از معیارهای پذیرش منتشر شود.
- URLها، نام پارامترها و query stringهای فعلی حفظ شوند. route groupهای `(public)`، `(auth)` و `(account)` بخشی از URL نیستند.
- بین Next و Vite از `<a href>` یا navigation کامل استفاده شود؛ `Link` هر router فقط برای مسیرهای متعلق به همان اپ باشد. React Router ممکن است یک URL منتقل‌شده را در سمت Vite بگیرد؛ همهٔ لینک‌های ورودی آن صفحه باید اصلاح شوند.
- در دورهٔ هم‌زیستی، احراز هویت فعلی با کلیدهای `access_token` و `refresh_token` در localStorage و API نسبی `/api` حفظ شود. origin مرورگر باید ثابت بماند.
- بررسی نقش در رابط کاربری جای کنترل مجوز در Django را نمی‌گیرد. دادهٔ خصوصی بدون احراز هویت در سرور واکشی یا به صورت عمومی cache نشود.
- بازطراحی بصری، تغییر قرارداد API و بازنویسی بک‌اند را وارد همین مهاجرت نکنید. هر تغییر رفتاری مستقل ثبت شود.

## دستور کار تکرارشونده برای هر صفحه

1. فایل صفحه، CSS، hooks، store، کامپوننت‌ها، endpointها و لینک‌های ورودی/خروجی آن فهرست شوند. رفتار موجود معیار است؛ ستون «بررسی ویژه» جای خواندن کد صفحه را نمی‌گیرد.
2. مسیر مقصد ساخته شود و وابستگی‌های لازم با نسخهٔ سازگار به package پوسته اضافه شوند؛ کل `App.jsx` و BrowserRouter در Next mount نشوند.
3. wrapper سرور صفحه، metadata و مرزهای client مشخص شوند؛ `loading`، `error` و حالت خالی متناسب با روش واکشی پیاده شوند. error boundary تعاملی باید client باشد.
4. رفتار router و فرم‌ها منتقل شود؛ وابستگی به route state، history، query و hash صریحاً بازبینی شود.
5. مالک مسیر در ابزار navigation تغییر کند و همهٔ لینک‌های قدیمی که به آن می‌رسند بررسی شوند. پس از ساخت صفحه در Next، درخواست مستقیم همان URL دیگر به fallback قدیمی نمی‌رسد.
6. چک‌لیست پذیرش زیر اجرا شود؛ build اپ جدید و بررسی‌های مرتبط اپ قدیمی موفق شوند.
7. تغییر همان صفحه و وابستگی‌هایش در یک PR/کامیت قابل بازگشت ثبت شود؛ سپس در محیط مشترک منتشر و خطاها بررسی شوند.
8. نسخهٔ قدیمی تا پایان بازهٔ پایش توافق‌شده نگه داشته شود؛ حذف آن مرحله‌ای جدا باشد.

- [ ] رفتار موفق، loading، empty، خطای اعتبارسنجی، قطعی API، 401/403 و شناسهٔ نامعتبر بررسی شده‌اند.
- [ ] موبایل و دسکتاپ، RTL، فونت، تم، focus، صفحه‌کلید و reduced motion با خط مبنا تطبیق دارند.
- [ ] hydration warning، دسترسی نامعتبر به browser API، خطای console و asset ناموفق وجود ندارد.
- [ ] دادهٔ خصوصی در HTML عمومی یا cache مشترک قرار نگرفته و مجوزها در API اعمال می‌شوند.
- [ ] refresh توکن، خروج، returnTo و عبور بین اپ‌ها درست است؛ فرم دوباره ارسال ناخواسته ندارد.
- [ ] build production موفق است و تست‌های مرتبط با رفتار واقعی همان صفحه اجرا شده‌اند.

## بازگشت یک صفحه

اگر رفتار بحرانی شکست خورد، نسخهٔ قبلی پوسته و مالکیت navigation را با هم برگردانید. برای بازگشت دستی، صفحهٔ Next مربوط را حذف/غیرفعال کنید تا fallback فعال شود؛ route قدیمی باید همچنان موجود باشد. پس از حذف route قدیمی، بازگشت نیازمند استقرار مجدد نسخهٔ قدیمی Vite نیز هست. originهای API را برای rollback یک صفحه تغییر ندهید. برگشت config معمولاً به build و استقرار مجدد نیاز دارد.

## فاز هفت — 404 و حذف Vite

- [ ] همهٔ ۳۲ مسیر جدول‌ها منتقل شده باشند و هیچ لینک/redirect فعال به مسیر متعلق به Vite باقی نماند.
- [ ] NotFound فعلی به `app/not-found.jsx` منتقل شود و پاسخ HTTP 404 بررسی شود. تا پیش از این مرحله، درخواست‌های ناشناخته همچنان به Vite می‌روند؛ وضعیت HTTP صفحهٔ 404 در وب‌سرور قدیمی نیز باید بررسی شود.
- [ ] fallback به Vite حذف شود؛ مسیرهای ناشناخته، فایل‌های ناموجود و پارامترهای نامعتبر دوباره تست شوند. catch-all عمومی برای پنهان‌کردن خطاها اضافه نشود.
- [ ] routeهای قدیمی، BrowserRouter، React Router و وابستگی‌های بلااستفاده پس از جست‌وجوی مصرف‌کنندگان حذف شوند.
- [ ] build و استقرار فقط با Next و Django انجام شود؛ Vite server و تنظیم HMR، وب‌سرور legacy و متغیر LEGACY_ORIGIN حذف شوند. خروجی rollback قبلی تا پایان پایش نگه داشته شود.
- [ ] اسکریپت‌های تست، CI، README و راهنمای اجرا به ساختار نهایی به‌روز شوند؛ `/migration` آزمایشی حذف شود.
- [ ] تست کامل جریان عمومی ← ورود ← ثبت سفر/خرید ← پیگیری ← مدیریت و گزارش مالی انجام شود.

**تعریف پایان:** اپ بدون اجرای Vite تمام مسیرها و assetها را ارائه می‌دهد، کنترل‌های دسترسی و جریان‌های مالی تأیید شده‌اند و fallback قدیمی از استقرار حذف شده است. بهینه‌سازی SSR، cache، تصاویر و طراحی نشست cookie پس از این نقطه با نیاز و معیار مستقل انجام می‌شود.
